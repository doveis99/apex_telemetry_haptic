# xHaptics Engine 분석 노트 — 1단계 (설정·UI·로그)

- 대상: Flydigi xHaptics Engine **5.0.2.6** (`C:\Program Files\Flydigi\Engine`, 2026-10-16 빌드), 이 PC에 설치된 그대로
- 날짜: 2026-10-27
- 방법: 설정 JSON, 캐시된 프로필 패키지, 웹 UI 번들, exe 안의 문자열, 엔진 로그를 읽기만 했음. 엔진을 실행하거나 패드로 출력을 캡처하지는 않았음
- 주의: APEX 6 Pro는 정식 출시 전이고 엔진·펌웨어가 계속 바뀜. 아래 값은 모두 이 버전의 스냅샷. Flydigi 파일은 저장소에 넣지 않고 수치와 구조만 적음

## 1. 엔진 구조

- 백엔드 세 가지: 실시간 오디오(`realtime-audio`), 적응형 트리거(`adaptive-trigger`), UDP 텔레메트리(`racing-telemetry`, UI 이름 "UDP haptics")
- 실시간 오디오 경로: 게임 프로세스의 WASAPI 루프백(48 kHz 필수) → 오토 게인(분석 대역 50~300 Hz) → 음성 검출(silero VAD, 음성이면 진동을 최소 5%까지 줄임) → 그립 DSP와 트리거 DSP(HPSS + 매퍼) → 퓨전(게임의 기본 럼블 + 오디오 질감) → 믹스 → Composer → HID 출력
- 서버가 내려주는 프로필이 로컬 기본값보다 우선함. 실제로 이 PC에서는 그립 게인이 로컬 기본값(0.3 / 0.8)과 달리 2 / 2로 받아져 있음. 같은 엔진 버전 안에서도 값이 바뀔 수 있다는 뜻

## 3. 오디오 → 햅틱 매퍼의 패턴

HPSS 프리셋은 모두 오디오를 세 대역으로 나눠 각각 반송파 하나에 실어요.

| 프리셋 | 저역 → 반송파 | 중역 → 반송파 | 고역 → 반송파 |
|---|---|---|---|
| 그립 hpss-balanced | 1~3 kHz → 60 Hz, +6 dB, 해제 20 ms | 3~6 kHz → 90 Hz, +8 dB, 10 ms | 6~12 kHz → 170 Hz, +10 dB, 5 ms |
| 그립 hpss-sharp | → 60 Hz, +2 dB, 20 ms | → 90 Hz, +6 dB, 10 ms | 8~12 kHz → 210 Hz, +16 dB, 5 ms |
| 트리거 hpss-punch | 1~2.5 kHz → 60 Hz, +4 dB, 10 ms | → 80 Hz, +6 dB, 5 ms | → 130 Hz, +8 dB, 3 ms |
| 트리거 hpss-vehicle (탈것) | 0.3~2 kHz → 60 Hz, +4 dB, 30 ms | → 85 Hz, +6 dB, 20 ms | → 150 Hz, +10 dB, 10 ms |

- 높은 소리일수록 높은 반송파에 실고, 게인은 더 주고(공진에서 멀어 약해지는 것 보상), 해제는 더 짧게(날카롭게) 해요. 어택은 모두 1 ms예요
- 1.0 클래식 프리셋(m1, layered)은 타격을 공진 주파수(65 Hz) 그대로에 싣고 어택 0.2~0.45 ms, 해제 18 ms로 짧게 끊어요. 배경은 타격이 나올 때 72~94% 덕킹해요

## 4. 트리거·그립 정책

- **트리거는 손가락이 올라가 있을 때만 울려요.** XInput으로 트리거 눌림을 읽어 10%부터 키우기 시작해 20~25%에서 최대가 돼요(`triggerMixStartPct` / `triggerMixFullPct`). XInput DLL을 못 불러오면 트리거와 그립 게이트를 닫는다는 로그 문구가 exe에 있어요
- 아래는 설정 이름으로 추정한 동작이라 캡처로 확인이 필요해요
  - 트리거가 울릴 때 그립을 20% 덕킹(`triggerDuckGripPct`)하고, 그립은 최소 50%를 남김(`triggerGripMinimumPct`)
  - 일정 시간 패드 입력이 없으면 그립을 닫음(`xinputActivityTimeoutSec` 30초, 서버 프로필 `gripActiveHoldSec` 900초)

## 7. Space Station 5.0 (웹) — 2026-10-27

- 데스크톱 Space Station 4.2.2.3에는 APEX 6(k6) 지원이 없고, 새 구조 기기는 웹 앱 `space_station.flydigi.com`("Space Station 5.0", WebHID)으로 보냄. 번들(`vendor-gpa6-core/codec/contract`, 진동·트리거 페이지 청크)을 받아 읽었음
- **0x53 명령 형식:** `[area, target, mode, ...params]`. 우리 실시간 활성화 프레임은 area 1(그립 `01 02 03 00 40`, 트리거 `01 12 02 40 00`)이고, Space Station은 area 0을 씀
- **area 0의 target은 좌우 코드:** 트리거 햅틱 페이지가 `target`을 `{left: 0, right: 1, both: 2}`로 보내고, both를 쓰면 왼쪽·오른쪽 기록을 둘 다 다시 읽어 확인함. 0x57 라우트 코드(0/1/2)와 같은 체계
  - mode 0 = 끔, mode 1 = 내장 트리거 햅틱 장면, mode 2 = 트리거가 그립 럼블을 따라 울림(params `[0, 64, 6]`, 진동 페이지의 트리거 왼쪽·오른쪽 스위치)
  - 내장 장면 12개(waveId 0~11). 반복형 4개는 주파수 간격 `[80,45,0]` 등 3단계, 단발형은 트리거 행정 구간(시작 50 / 80 / 178)에서 한 번. params `[id, 시작, 끝, 반복, 간격, globalGain 27~40, 64, 64, waveId, 255]`
- **펌웨어는 트리거 좌우를 따로 다룸:** 내장 장면을 왼쪽·오른쪽에 따로 걸 수 있음. 실시간 경로(area 1)에서 안 갈리는 건 하드웨어 한계가 아니라 우리가 보내는 프레임 문제일 수 있음
  - 가설: area 1의 target도 낮은 니블이 좌우(0 왼쪽, 1 오른쪽, 2 양쪽), 높은 니블이 부위(0 그립, 1 트리거). 그러면 `0x10` = 왼쪽 트리거, `0x11` = 오른쪽 트리거. 우리가 바꿔 본 mode 바이트가 아니라 target 바이트가 열쇠일 수 있음
- **모터 설정 RAM:** ramId 6, 64바이트. 0xA3(읽기, 16바이트 청크)과 0xA4(쓰기)로 다룸. [1] 왼쪽 트리거 mode, [2..11] 왼쪽 params, [12] 오른쪽 트리거 mode, [13..22] 오른쪽 params, 나머지 바이트는 모름. 슬롯별로 저장되는 온보드 설정으로 보임
  - 사용자가 트리거 장면이나 "그립 따라 울림"을 켜 두면 우리 출력과 섞일 수 있음. 읽기만 하는 0xA3으로 확인 가능
- **진동 세기 1~5단계:** 그립 세기는 온보드 프로필의 `vibration_motor_left/right` 커브 끝값. 햅틱 그립 모델은 128 / 166 / 204 / 230 / 255, 일반 모델은 51~255. 트리거 세기는 `vibration_trigger_left/right` 커브(좌우 따로). 이 커브가 우리 0x57 실시간 출력에도 걸리는지는 모름. ASB는 "Space Station 세기가 결과에 영향을 준다"고만 적음
- 웹 앱의 진동 테스트 버튼은 브라우저 Gamepad API의 dual-rumble이라 실시간 경로와 무관
- **2026-10-27 `tone.py trigger-target` 결과 (펌웨어 9.0.5.5, 유선, 20%, 110 Hz, route BOTH):** target 0x10·0x11·0x12 모두 양쪽 손가락에서 기준음과 "비슷". 실시간 트리거를 이 바이트로 한쪽만 켜지는 못했음
  - 0xA3 모터 RAM 읽기는 동작함. 사용자 패드의 온보드 설정은 양쪽 트리거 모두 mode 2(그립 진동 따라 울림, params `00 40 06`)
  - RAM은 32바이트씩 두 블록으로 보임. 0x00~0x1F가 area 0, 0x20~0x3F가 area 1. 각 블록은 `[머리 0x02] [11바이트 기록 ×2: mode + params 10] [2바이트 기록 ×2: mode + param]`
  - 시험 전에는 area 1이 비어 있었고, 끝난 뒤(기본 프레임으로 켠 상태)에는 우리 그립 프레임(target 0x02, mode 3)이 0x21·0x2C 두 기록에, 트리거 프레임(target 0x12, mode 2)이 0x37·0x39 두 기록에 써져 있었음. 낮은 니블 2 = 양쪽이라는 해석과 맞고, **실시간 설정에도 트리거 좌·우 기록이 따로 있음**
  - 다만 끝난 뒤 읽기는 기본값(0x12)으로 되돌린 다음이라, 0x10·0x11이 한쪽 기록만 쓰는지는 아직 모름. 한쪽만 쓰는데도 양쪽이 울렸다면 실시간 트리거 출력이 기록과 상관없이 양쪽으로 나가는 것(펌웨어 한계)이고, 아니라면 펌웨어가 그 target을 다르게 받는 것
- **2026-10-27 `tone.py trigger-ram` 결과 (진동 없이 켜고 끄며 RAM 읽기):** 0x10은 왼쪽 트리거 기록(0x37)만, 0x11은 오른쪽(0x39)만, 0x12는 둘 다 씀(mode 2, param 0x40). 그립 프레임은 매번 그립 좌·우 기록(0x21·0x2C, mode 3, param 0x40)을 씀. 끄면 area 1이 깨끗이 비워짐
  - **결론:** target 바이트의 뜻(낮은 니블 = 좌우)은 맞았고, 펌웨어는 한쪽만 켠 상태를 정확히 기록함. 그런데도 체감은 양쪽이 똑같았음. mode 0x00으로 기록을 "끔"으로 만들었을 때도 트리거가 울렸으니, 펌웨어 9.0.5.5의 실시간 트리거 출력은 area 1 트리거 기록과 상관없이 양쪽 액추에이터로 나감
  - 남은 변수 하나: 온보드 area 0의 트리거 설정이 양쪽 다 "그립 진동 따라 울림"(mode 2)으로 켜져 있었음. 이걸 끈 상태에서 trigger-target을 다시 해 봐야 이 설정이 섞인 건 아닌지 확실해짐

## 11. 2 kHz 모드: 0x57 첫 바이트 bit 7 — 2026-11-08

**출처:** 펌웨어 9.0.6.8의 0x57 처리 코드를 정적 분석한 다른 사람의 설명(2026-11-08 공유, 그쪽도 패드 측정 전). 요지:
- 출력단은 원래 2 kHz. bit 7(0x80)이 켜져 있으면 리포트의 8샘플을 직선으로 이어 16개로 늘리고, 8 ms마다 16개를 꺼내 씀 → 지금 앱(그리고 Flydigi 엔진, ASB)은 1 kHz 데이터를 2 kHz로 늘려 재생하는 셈
- bit 7을 끄면 8샘플을 그대로 큐(96칸)에 넣음 → 4 ms마다 하나씩, 처음에 프라이머 2개를 보내면 2 kHz 데이터(나이퀴스트 1 kHz)
- 9절의 4 ms 실험이 거칠었던 이유: bit 7을 켠 채 4 ms면 4 kHz가 2 kHz로 빠지니 약 45 ms 만에 큐가 차고 넘친 샘플은 버려짐
- 출력단도 직선 보간이라 700 Hz −3.6 dB, 900 Hz −6 dB. 트리거는 리포트당 한 바이트를 양쪽이 공유. 타이밍은 ±1 ms 안이어야 함(큐가 비면 마지막 값을 2 ms 유지)

**확인 방법:** `tone.py rate-2k --record "Analogue 1/2(Audient iD14)"`가 같은 톤(양쪽 그립 25%: 700, 900, 300, 160 Hz, 200→950 Hz 스윕)을 1k(지금 앱) → 2k(bit 7 끔, 4 ms, 프라이머 2) → 1k 다시(쥔 자세 대조) → old4(bit 7 켬, 4 ms, 9절 재현) 순서로 울리고 마이크로 녹음. 실제로 보낸 샘플과 보낸 시각을 json에 남기고, `tools/rate2k_analyze.py`가 같은 주파수끼리 모드를 비교(방·껍데기 영향이 상쇄됨)하고 패드 모델 셋을 시뮬레이션해서 맞춰 봄: claim(위 설명대로), dup-bit7(bit 7이 샘플을 잇지 않고 두 번씩 복제 = 11-04 녹음이 맞아 보였던 1 kHz 샘플-홀드), ignore-bit7(bit 7을 꺼도 아무 변화 없음). 각 모델로 만든 가짜 녹음(지터·방 특성·잡음 포함) 셋 모두 분석기가 맞는 모델을 골랐음. 직접 들어 보기: `tone.py tone --freq 700 --rate 2k`

## 12. 앱에 넣은 2 kHz 출력 — 2026-11-08

11절 결과로 앱(Rust)에 **2 kHz 출력** 스위치를 넣음(창 아래쪽, 명령줄 `--rate 2k`, 설정 `app.output_2k`, 기본 꺼짐). `src/rate2k.rs`.

**설계:** 합성기는 1 kHz 그대로(효과·기본값·사용자 튜닝·파이썬과의 비트 일치를 건드리지 않음). 8 ms 블록 하나를 2 kHz 반쪽 둘로 바꿔 bit 7을 끄고 4 ms 간격으로 보냄.
1. **펌웨어의 직선 잇기를 PC에서 똑같이:** `y[2i] = (x[i-1]+x[i])/2`, `y[2i+1] = x[i]`(11절 claim 모델과 같은 정렬). 그래서 느껴지는 대역의 응답(직선 잇기의 cos²(πf/2000): 190 Hz −0.8 dB, 300 Hz −2 dB)이 사용자가 튜닝한 그대로임
2. **그 위에 거울상 저역 통과:** 타원 4차, 0.05 dB 리플, 40 dB, 경계 420 Hz(`scipy.signal.ellip(4, 0.05, 40, 420, fs=2000)`, 0 Hz에서 0 dB로 맞춤). 400 Hz까지 ±0.05 dB, 600 Hz −24 dB, 700 Hz 이상 −41 dB 넘게 → 직선 잇기와 합쳐 400 Hz 아래 성분의 거울상(600 Hz 위)을 33 dB 넘게 깎음. 지연 1.3~1.6샘플(0.7 ms). 후보 6개(타원 4·5차, 역체비셰프 5·6차, 버터워스 6차) 중 통과대역이 평평하고 지연이 가장 짧은 것. 울림(임펄스가 −40 dB까지 9~15 ms, 계단 넘침 17~20%)은 모두 비슷
3. **틱은 2 kHz 한 샘플로:** 저역 통과에 넣으면 틱이 뭉개지므로 합성기가 틱을 따로 내놓고(`Synth::native_ticks`, 블록의 `ticks`) 저역 통과 뒤에 더함. 세기는 1 kHz 틱을 직선으로 이은 삼각형의 넓이(높이의 2배)를 한 샘플에 → 모터를 미는 양은 같고 모서리만 날카로움. 소프트 리미터는 틱이 더하는 몫(`out(나머지+틱) − out(나머지)`)으로 넘겨서 1 kHz와 같게 눌림(블링커 첫 샘플: 따로 누르면 저음이 15% 셌음). 모터 공진 컷(`ResonanceCut::at_rate`, 2 kHz)을 틱에도 걸고, 상한(그립 127, 트리거 102)에 걸린 틱의 나머지는 다음 샘플로 넘김. 저역 통과 지연에 맞춰 한 샘플 늦게 둠
4. **트리거 경로:** 합성기가 조용해져(MUTE) 저역 통과가 조금 더 울리거나 늦은 틱이 남으면 그 반쪽은 BOTH로 보냄. 1e-3 아래로 울림이 잦아들면 정확한 0으로 돌아가서 MUTE·유휴 판정이 그대로 됨(150 Hz 60 세기 톤이 끝나고 32 ms 안)
5. **스트림:** 블록마다 `upsample`(bit 7)을 보고 다음 마감을 8 ms 또는 4 ms 뒤로 잡음. 링크는 2 ms 칸에 리포트 하나라 4 ms 사이엔 프레임 하나만 더 들어감 → 2 kHz 블록에서는 0x53 재확인 두 프레임과 트리거 방향을 바꿀 때 떠나는 쪽 끄기를 블록마다 하나씩 뒤로 미룸(나갈 때 그때의 경로로 만들고, 그사이 다시 그쪽으로 돌아왔으면 끄기는 버림). 그 블록에서 방향 켜기를 이미 보냈으면 미룬 것은 다음 블록으로. 1 kHz는 예전 순서 그대로
6. 디버그 기록·미터는 8 ms 블록 단위 그대로(틱도 최대값에 들어감). 효과 테스트(▶)도 같은 길로 나감. 주행 중에 켜고 끄면 다음 8 ms 블록부터 바뀜

**PC에서 잰 것:**
- 시나리오(기본 설정)에서 1 kHz 샘플을 직선으로 이었을 때 500~1000 Hz 거울상: 그립 전체 대비 −25 ~ −33 dB, 트리거는 100 Hz 반송파의 900 Hz 선이 −26 ~ −30 dB로 늘 깔림 → 2 kHz 출력에서는 33 dB 넘게 더 깎임
- 블링커 테스트를 1 kHz(패드가 직선으로 이은 것)와 2 kHz 출력으로 비교: 20~120 Hz는 3% 안으로 같음(150 Hz는 +3%: 한 샘플 틱이 1 ms 삼각형보다 평평해서), 600~900 Hz는 틱 덕에 1.5~18배
- 박자(`cargo run --release --example stream_timing -- 20 2k load`, 버리는 링크, 논리 코어 16개 모두 바쁨): 2 kHz 보고 간격 중앙 4.012 ms, 최대 4.371 ms, 4 ms보다 0.5 ms 넘게 늦은 것 0/4999. 부하 없을 때 최대 4.656 ms, 0.5 ms 넘게 늦은 것 11/4999, 1 ms 넘는 것 0. 2 kHz 단계는 블록당 약 1 µs

**아직 모르는 것(패드로 확인할 것):**
- 패드에서 실제로 느낌이 같고 잔음이 줄었는지. 녹음으로 확인하려면 같은 효과 테스트를 스위치 끄고/켜고 번갈아
- 실제 쓰기 시간: 링크가 리포트마다 2 ms 칸을 쓰면 4 ms 안에 블록 + 프레임 하나가 꽉 참. 위 박자 측정은 쓰기가 0인 가짜 링크라 이 부분이 빠짐. 앱의 "지난 세션: 지연 프레임"(2 kHz는 4 ms를 넘긴 것)과 디버그 기록 `gap_ms`로 볼 것
- 무선 끊김이 2배 많은 리포트로 늘어나는지: 11절 시험에서는 모드 차이를 못 가렸음(같은 모드도 바퀴마다 7배 오락가락)
- 틱이 날카로워진 만큼 딸깍 소리가 커짐(블링커 900 Hz 18배). 귀에 거슬리면 TICK_SHARE나 효과별 세기로 줄일 것
