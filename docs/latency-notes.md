# 지연 분석 노트

- 날짜: 2026-11-03
- 대상: 0.17.1 (`apex6.py`, `effects.py`, `ats_haptics.py`)
- 방법: 실제 창(`gui.App`)과 출력 루프(`Apex6.stream`)를 그대로 돌리고, 패드만 보고서를 버리는 가짜로 바꿔서 블록이 나가는 간격을 쟀음. CPU 부하는 일반 우선순위로 무한 루프를 도는 프로세스 16개(논리 코어 수만큼). PC는 Ryzen 7 5800X3D(8코어 16스레드, 효율 코어 없음), Windows 11, Python 3.12.10
- 패드 쪽(USB 쓰기 시간, 패드 안의 버퍼)은 재지 못했음. 패드 없이 잰 값이라 게임 프레임에서 손까지의 전체 지연은 아님

## 1. 지연이 쌓이는 경로

| 단계 | 지연 | 성격 |
|---|---|---|
| 게임 프레임 → 공유 메모리 | 게임 프레임마다 한 번 (60fps면 16.7 ms 간격) | 플러그인 동작, 바꿀 수 없음 |
| 공유 메모리 → 다음 8 ms 블록 | 0~8 ms, 평균 4 ms | 패드가 8 ms마다 보고서를 받으므로 구조적. 블록을 만들기 직전에 읽으니 이미 최소 |
| 텔레메트리 읽기 | 0.04 ms | 트럭 6바퀴 + 트레일러 16바퀴 기준 |
| 블록 합성 | 0.14 ms (중앙값), 0.27 ms (p99) | 이번에 0.19 / 0.38 ms에서 줄임 (아래 2절) |
| 출력 스레드가 제때 깨어나기 | 부하가 없으면 대개 0.4 ms 안쪽 (최대 0.7 ms). 모든 코어가 바쁘면 최대 9 ms 늦었음 | 이번에 고침 (아래 2절) |
| USB 쓰기 | 재지 못함 | `StreamStats.max_write_ms` (명령줄 `ats_haptics.py`가 연결을 놓을 때 출력) |
| 패드가 8개 샘플을 8 ms 동안 재생 | 이벤트(요철, 변속 등)는 블록 첫 샘플부터. 지속 효과의 세기 변화는 블록 끝까지 직선으로 올라감 (평균 4.5 ms) | 의도. 세기가 계단처럼 바뀌면 딸깍 소리처럼 느껴짐 |

## 2. 이번에 고친 것

### 출력 스레드 우선순위 (가장 큼)

출력 스레드가 일반 우선순위라서 게임 스레드와 CPU 차례를 다퉜음. 모든 코어가 바쁠 때 블록 간격:

| | 블록 수 | 1 ms 넘게 늦은 블록 | 가장 늦은 블록 |
|---|---|---|---|
| 일반 우선순위 (이전) | 7,756 | 525 (6.8%) | 9 ms |
| time-critical (지금) | 17,206 | 7 (0.04%) | 6 ms |

- `Apex6.stream`이 도는 동안만 그 스레드를 `THREAD_PRIORITY_TIME_CRITICAL`로 올리고, 끝나면 원래대로 돌려 놓음. 주행, 효과 테스트, 모터 보정, `tone.py`가 모두 이 함수를 거침
- 블록 하나에 0.15 ms 정도라 게임이 내주는 몫은 코어 하나의 2% 정도
- MMCSS("Pro Audio")도 결과가 같았지만 time-critical이 더 단순해서 이쪽을 씀. `THREAD_PRIORITY_HIGHEST`는 덜 됐음 (1 ms 넘게 늦은 블록 2개, 최대 3 ms)
- 남은 몇 개는 GUI 스레드가 GIL을 쥔 채 게임 스레드에 밀렸을 때로 보임 (확인하지는 않음)

### 블록 합성 시간 27% 단축

60초 시험 주행 7,500블록 기준, `Synth.render` 중앙값 188 → 137 µs, p99 376 → 270 µs. 텔레메트리를 읽은 뒤 패드에 쓰기까지의 시간이라 그만큼 지연이 줄어듦.

- `Equalizer.pair()`: 블록마다 소리 나는 효과와 버스트 하나하나의 주파수로 곡선 보간과 공진 필터 크기를 다시 계산했음 (합성 시간의 6분의 1). 주파수별로 결과를 저장해 둠 (`PAIR_CACHE`)
- `side_surface()`: 블록마다 바퀴의 재질 이름으로 노면을 다시 찾고 섞었음 (10%). 재질 이름 조합별로 저장해 둠
- 바꾸기 전후 60초 주행의 출력 18만 샘플이 비트 단위까지 같음

### 정리

- 쓰이지 않던 `apex6.MOTOR_ENABLE` 삭제
- `Runner.render`가 이벤트가 없는 블록에서도 매번 시각 문자열을 만들던 것 정리
- 줄 길이 정리 (`telemetry.py`, `tests/test_effects.py`의 import)

## 3. 지연처럼 보이지만 의도한 것

블록 처리보다 훨씬 큰 지연이지만 모두 이유가 있어서 바꾸지 않았음. 게임에서 늦다고 느껴지면 손댈 곳은 여기.

- **요철은 게임 프레임 하나 늦게** (60fps에서 17 ms, 30fps에서 33 ms): 게임이 한 프레임만 튀었다 돌아오는 서스펜션 값을 보내는데, 2026-10-31 주행에서 요철 노크의 80%가 이것이었음. 다음 프레임을 봐야 걸러낼 수 있음 (`effects.SPIKE_*`). 게임 화면과 소리도 텔레메트리보다 1~3프레임 뒤에 나오니 그 정도로는 화면보다 늦지 않을 것 (추론, 잰 적 없음)
- **변속 '철컥'은 기어가 바뀌고 0.14초 뒤**: 게임이 내는 이튼 풀러 변속음 녹음의 타이밍 그대로라 소리와 함께 옴 (`SHIFT_HITS`, 레버가 빠지는 '툭'은 0.02초). 레인지 셀렉터/스플리터의 공압 변속음 (0.12~0.18초 뒤, 노브 소리는 바로), 시동 (스타터는 바로, 엔진이 걸리는 건 1.04초 뒤), 트레일러 연결 (0.6초 동안 덜컹거림)도 같은 이유
- **노면 거칠기 평균** (76 ms, `ROUGH_TAU`): 노면 진동의 세기가 따라가는 속도. 요철 노크와는 무관
- **캡 흔들림** (25 ms, `CAB_SWAY_TAU`): 게임 프레임 사이의 계단을 펴는 정도
- **휠스핀은 멈출 때만 150 ms**: 시작은 바로

## 4. 재 봤지만 원인이 아니었던 것

- **GUI와 GIL**: 슬라이더를 초당 30번 움직이거나, 0.5초마다 프리셋 전체를 다시 적용하거나, 0.7초마다 언어를 바꿔 창 전체를 다시 만들어도 늦은 블록이 없었음. tkinter가 Tcl을 부를 때마다 GIL을 놓기 때문. 다만 순수 파이썬 계산을 오래 하는 스레드가 생기면 Windows에서는 GIL을 넘겨받는 데 최대 16 ms가 걸림 (따로 만든 시험에서 측정, Windows 기본 타이머 단위 15.6 ms). 지금은 그런 스레드가 없음
- **가비지 컬렉션**: 15~30초씩 여러 번 재서 0세대 최대 0.4 ms, 1세대 최대 0.8 ms. 2세대는 한 번도 돌지 않았음
- **디버그 기록**: 켜 두면 블록마다 35 µs (p99 76 µs)
- **sleep 정밀도**: 파이썬 3.11부터 Windows에서 고해상도 타이머를 써서 블록 간격 중앙값 8.01 ms
- **창 최소화**: Windows 11이 최소화된 창의 프로세스를 느리게 돌릴 수 있는데, 이 PC에서는 차이 없었음. 효율 코어가 있는 인텔 CPU에서는 다를 수 있음

## 5. 아직 모르는 것

- 실제 패드의 USB 쓰기 시간 (유선과 2.4 GHz 동글 각각). 명령줄로 돌리면 연결을 놓을 때 `write avg / max`가 찍힘
- 패드가 보고서를 받고 재생을 시작하기까지의 시간. 펌웨어 안의 일이라 여기서는 못 잼
